# 0.5.1 批处理资源保护与验证

## 事故与修复范围

2026-11-05 的独立远端调度脚本曾同时启动32个spawn进程进行JAX冷编译。重启前内核日志确认发生global OOM，杀掉了多个Python进程；当时被杀进程的匿名驻留内存约2.0～2.3 GiB。旧标准CPU Pipeline的fork共享模型、峰值预算和可用内存预留没有移入该临时调度器。这是调度保护缺失，不能归因于输入动作质量。

0.5.1 已将资源保护接入正式 `dex-frax batch`，包括固定模式和自动模式。求解权重、接触/限速/碰撞/姿态质量门槛不变。

## 已实现

- CPU affinity/配额限定执行槽；单线程数值库；默认预留主机内存10 GiB、磁盘80 GiB。
- 每个在途动作预估4 GiB加每输出帧64 KiB；派发前预留尚未分配的峰值内存。32槽不保证任意时刻都能同时跑32个动作。
- 全局批次锁；可通过 `DEX_FRAX_CPU_LEASE_FILE` 与旧标准Pipeline使用同一把运行锁。
- Frax JIT准备/编译使用单路文件锁，求解阶段释放；进程异常退出不会永久占锁。
- Linux并发CLI通过用户systemd scope设置MemoryMax/MemoryHigh，禁用本scope交换；限额创建或验证失败时拒绝启动。
- XML→MJB模型数组校验；spawn进程内复用MjModel，独立MjData；不fork已初始化的JAX，不声称跨spawn共享模型对象。
- 转换身份/网格哈希先冻结、末尾复验；闲置进程回收、分配器内存释放；记录PSS、实际并发、cgroup限额和采样峰值。
- 按动作长度设置超时；STOP、总预算及资源不足会终止本批次拥有的工作进程，阻止未完成导出进入accepted.json。

## 实测

| 检查 | 结果 |
|---|---|
| 本地完整测试，包含授权私有回归样例 | 130 passed |
| Linux资源调度、MJB与原级联回归 | 24 passed |
| 编译进程被kill后的文件锁释放 | 通过 |
| 32槽但仅能容纳2个峰值预算的模拟 | 实际仅派发2个 |
| 内存不足、紧急内存阈值、预算终止 | 不新增任务／清理本批次任务，无不完整训练导出被采用 |
| 本地真实LAFAN片段 | 300帧通过；根位置、根旋转、关节角与0.4.1对照逐值一致 |
| Linux单进程，8 GiB硬限制 | 两条小样完整转换；LAFAN accepted、BONES review；约99秒 |
| Linux双进程自动级联，12 GiB硬限制 | 确认最大实际并发2；两条小样终态明确；约123秒 |
| 双进程初解复用 | BONES hybrid的initial_reuse.used=true |
| Linux单/双进程结果对照 | 两条小样的frax根位置、根旋转、关节角均逐值一致 |
| 实际合格NPZ检查 | 与对应PKL逐值一致，哈希、关节名称和有限值检查通过 |

双进程验证采样峰值：单worker PSS 3,147,834,368字节（约2.93 GiB）；worker PSS合计4,190,175,232字节（约3.90 GiB）；scope使用量4,666,408,960字节（约4.35 GiB）。这些是采样值，不宣称捕获了每个瞬时峰值。

双进程验证中LAFAN在frax阶段通过；BONES依次跑完frax、hybrid和V8后仍为review，未因此放宽质量要求。单进程为固定frax、双进程为自动级联，不能用两者墙钟时间直接计算并行加速比。

## 验证边界

没有重新启动32路满载或全库转换。32路满载稳定性、长动作峰值与全库吞吐仍需渐进实测；4 GiB基数是当前保守起点，不能替代各类动作的峰值测量。Linux硬内存隔离旨在把超额限制在本批次内，不能视为任意资源负载下的系统可用性保证。macOS不具备本实现的cgroup硬限制。
